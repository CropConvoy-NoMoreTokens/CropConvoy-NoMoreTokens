# Contract agreement v0.1

P4 is the contract owner. The starter defines the initial agreement; the team should review it before splitting work. API types/validators live in api/src/core/contracts.ts. JSON schemas are exported to contracts/schemas.json. All owners must agree before changing a field or signature. No shared workspace package or production import outside api/ or web/.

## Common rules

- Point: `{lat, lng}`; GeoJSON: `[lng, lat]`.
- Crop: `tomato | potato | carrot`.
- Quantity: positive whole kg, maximum 2147483647 to fit PostgreSQL integer columns; distance: meters; duration: seconds. Road measurements may be fractional; round the final distance-based money charge, not the route geometry.
- Prices/totals: safe integer LKR minor units; 100 = Rs. 1.00. Check multiplication and addition for safe integer overflow.
- Timestamps: UTC ISO 8601 strings ending in Z. Display Asia/Colombo. Extraction receives explicit localTimeContext.
- IDs: UUID strings. Record IDs are generated by the server. Demo actor IDs are supplied by the client and are synthetic, not authorization.
- Request objects are strict; unknown fields are rejected. Publishing requires `confirmed: true`.
- Request bodies are limited to 64 KB; per-process demo limit is 60 API requests per minute per IP.

## Envelopes

Every successful endpoint, including health, returns:
```json
{"data": {}, "meta": {"mode": "stub", "persistence": "memory", "requestId": "server-generated UUID"}}
```

`mode`: `stub | live | deterministic_fallback`. A live provider failure must be labeled fallback if deterministic work continues. The starter is `stub`; it never labels a fixture as a live AI result. `persistence`: `memory | postgres`; setting a database URL does not itself change this label. Update it only when repositories actually persist.

Errors:
```json
{"error": {"code": "VALIDATION_ERROR", "message": "Check the submitted fields", "fields": [{"path": "quantityKg", "message": "..."}]}}
```

Statuses: 400 malformed JSON; 403 unapproved browser origin; 404 missing record/endpoint; 409 stale/conflicting decision; 413 oversized body; 422 invalid input; 429 rate limit; 503 missing integration/dependency. All responses include X-Request-Id. A valid search with no suitable match is HTTP 200.

## Endpoint agreement

POST body schemas are in contracts/schemas.json. The return type below is inside the `data` envelope.

| Method/path | Input | data type / behavior | Owner |
|---|---|---|---|
| GET /health | none | `{status:'ok', version, implementation}` | P2 |
| GET /ready | none | DB-backed readiness; 503 in starter | P2 |
| POST /api/harvest/extract | ExtractInput | ExtractResult; never publishes | P2 |
| POST /api/listings | ListingInput | Listing; 201 | P2 |
| GET /api/listings/:id | UUID path | Listing or 404 | P2 |
| GET /api/orders | none | Order[] | P2 |
| POST /api/orders | OrderInput | Order; 201 | P2 |
| GET /api/trips | none | Trip[] | P3 |
| POST /api/trips | TripInput | Trip with persisted full road geometry; 201, currently 503 | P3 |
| POST /api/plans/generate | `{listingId}` | GenerationResult | P4 |
| GET /api/plans/:id | UUID path | Plan or 404 | P4 |
| POST /api/plans/:id/decision | `{decision:'accept'\|'reject'}` | Updated Plan; currently 503 | P4 |

Listing/Order responses add `id`, `status`, and `createdAt` to their inputs. Trip adds those plus `routeGeoJSON`, `routeDistanceM`, `routeDurationS`, `routeProvider`, `routeProfile`. Listing's `confirmed` is the validated publication input, mapped to seller_declared in the database.

## Internal boundaries

All route modules export registerRoutes(router, deps, serviceOrRepository). api/src/app.ts constructs services and registers routes once; P2 owns that wiring.

```ts
// P2: modules/market
extractHarvest(input: ExtractInput, deps: Dependencies): Promise<ExtractResult>
findMarket(listingId: string, deps: Dependencies,
  repository: MarketRepository, signal: AbortSignal): Promise<MarketResult>
createMarketRepository(deps: Dependencies): MarketRepository
// repository: createListing, getListing, createOrder, listOrders

// P3: modules/logistics
createLogisticsService(deps: Dependencies): LogisticsService
// service: listTrips(), createTrip(input), evaluate(marketResult, signal), getQuote(quoteId)

// P4: modules/advocate
reviewOptions(input: ReviewInput, deps: Dependencies,
  signal: AbortSignal): Promise<ReviewResult>

// P4: modules/workflow
createWorkflowService(deps: Dependencies, market: MarketRepository,
  logistics: LogisticsService): WorkflowService
// service: generate(listingId), getPlan(id), decide(id, decision)
```

Dependencies expose `db`, `llm`, `routing`, `clock`, `mode`, `persistence`, `maxPlanMs`; all are interfaces with replaceable implementations. Do not call another module over HTTP. Keep fakes inside tests. P3 can query listing/order records through its own repository or agree on typed repository injection with P2.

## Quote handoff

LogisticsResult contains quote IDs and summaries. LogisticsService.getQuote(quoteId) returns the authoritative full QuoteSnapshot; P3 owns its implementation and backing repository. Workflow loads those snapshots and the listing into ReviewInput (`{listing, quotes}`) for advocate review. P4 revalidates source IDs, rule outcomes and amounts, then persists the snapshot with the Plan. The initial QuoteSnapshot/Plan types are in contracts.ts; full runtime validators remain P4 work. Do not compute a recommendation using the summary alone or let the browser supply authoritative snapshots. For isolated tests, P4 supplies a fake LogisticsService including getQuote; no live routing is required.

GenerationResult: `{outcome, plan, alternatives, rejections, trace, searchComplete}`. `plan` is null unless a real proposal has been validated and saved. The starter returns no_feasible_plan with searchComplete=false and BACKEND_PENDING context; do not show this as a completed real search. Trace contains observable actions/outcomes, never hidden model reasoning.

## Coordination limits and decisions

- At most 2 model turns per role; 3 buyer candidates; 6 routed combinations total; 1 alternative attempt.
- A maximum 45-second generation deadline; propagate AbortSignal to every model/routing request. P4 still needs to implement hard deadline enforcement and partial-result handling.
- Hard filters: exact crop, sufficient demand, partial-fill policy, sufficient trip capacity, simple route, pickup before delivery, snap/corridor tolerances, readiness, deadline, detour, minimum net.
- Confirm interpretation of allowsPartial at kickoff: the plan's core scope requires it enabled for candidate orders. Do not silently broaden policy based on an exact-quantity order.
- Net = quantity × unit price − transport. Transport = base + round(extra meters / 1000 × per-km rate) + handling. Price only the incremental detour.
- Plan states: proposed → farmer_accepted_pending_confirmations or rejected. Before acceptance, check expiry and current source records against the quote. Repeated same decision returns same state; conflicting decisions return 409. No demand/capacity decrement.
